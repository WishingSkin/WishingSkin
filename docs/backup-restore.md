# 备份与恢复

备份命令面向停写后的 WishingSkin，不读取或执行 SQL dump，也不能替代 BS 迁移快照。动态插件恢复会执行可信插件包中已应用的建表迁移。当前格式为 1，要求数据库 schema 与当前程序完全一致（当前为 21）；没有自动跨版本恢复或 schema 降级。旧 schema 备份需要先用匹配版本恢复到独立目标，再用新程序执行 `migrate`；不能直接交给 schema 21 程序恢复。

## 保存范围

目录包含完成清单 `manifest.json`、业务表的 JSONL 和 `textures/`。账号及密码哈希/盐、角色 UUID 与绑定、材质归属/描述/公开及下架状态、审核元数据、衣柜别名、账号验证状态、加密的 TOTP 密钥与恢复码摘要、OIDC/外部身份绑定、OAuth2 客户端、站点设置与签名私钥、迁移状态、管理审计及字段变更详情、举报、余额和积分流水均保留；另含独立的 `legacy_reports` 旧举报历史及其孤立编号、原时间文本和长正文，以及 `user_profiles` 中的头像来源、上传头像和跟随角色设置。昵称保存在账号表中，Logo、主题、公告格式与官方模块配置随站点设置保留。整数按十进制字符串保存，避免大余额或历史编号精度损失；NULL 保持 NULL。

OIDC 身份绑定和加密配置、首页区块与背景、公告历史进入备份。网页会话、游戏令牌、加入记录、邮件验证/找回链接、邀请码及 OIDC/OAuth2 令牌及待投递的扩展事件不进入备份，恢复后全部无效。用户重新登录；尚未完成验证的账号需要重发验证邮件。原库中的这些凭据不会因导出而被撤销。迁移 `pending` 阻止备份，`partial` 原样保留，恢复不把部分迁移标为完成。

每张表记录行数及 SHA-256，每份数据库引用的材质记录大小及独立 SHA-256，包括下架文件。孤立文件、上传临时文件及旧迁移目录清单不复制。原图片内容和存储 hash 不改变；SHA-256 用于检查副本，与自定义旧 hash 的计算方式无关。

`WS_PUBLIC_URL`、数据库连接和代理设置来自环境，操作人员需另外保存并配置。SMTP / Turnstile 的环境配置只作为初始值；通过后台保存后，数据库中的 `service_config` 密文优先并随业务备份原样保留，恢复后需要原设置密钥才能使用。密钥默认位于 `<WS_TEXTURE_DIR>/.settings.key`，可通过 `WS_SETTINGS_KEY_FILE` 指定独立路径；**业务备份不包含此密钥文件，必须单独安全备份并限制访问**。不要把服务密码、Secret 或密钥写进核对报告。

恢复完成后、启动服务前，将对应的原密钥安全放到目标配置路径。使用默认路径时，等待 `restore` 创建材质目录后再复制密钥。存在服务配置密文但缺少密钥时，程序拒绝启动；错误的 32 字节密钥无法解密配置，`/readyz` 和相关配置接口返回 503，不会静默回退到环境配置。丢失密钥意味着无法恢复这些服务秘密。数据库设置表还包含签名私钥，整个备份属于敏感数据，必须放入受控目录；备份格式不加密，摘要也不提供来源认证。Windows 的 `0600` 不能代替 NTFS ACL。

## 新版 Compose 的持久化目录

PostgreSQL 和 MySQL Compose 均把数据库、材质和 `/data/backups` 放在独立命名卷中。后台定时备份可把 `/data/backups` 设为目标目录；该卷会在容器重建时保留，但仍与应用在同一 Docker 主机。按灾备要求定期将备份副本移到独立主机或离线介质，并保护备份与 32 字节设置密钥。更新 Compose 文件不会删除已有卷；不要对本项目运行 `docker compose down -v`。

## 动态插件

安装的包、已确认权限、配置、KV 数据和插件 SQL 表一并进入备份。插件 ZIP 保存在 `plugins/`，自定义表以 JSONL 保存，二进制列使用 Base64。已卸载插件的数据也保留，备份会从保留的包中选择与已应用迁移匹配的版本。暂存的未安装升级不会在恢复时执行。

恢复不会启动插件进程。插件 SQL 表使用原数据库引擎恢复；没有插件 SQL 状态的核心数据仍可在 MySQL 与 PostgreSQL 间恢复。生成列、循环表依赖和缺少重建包的 SQL 表会使导出失败；此类插件需提供自己的备份流程。

自定义 `WS_PLUGIN_DIR` 时，恢复前也应改为新的空插件目录。默认目录随新材质目录创建。插件目录和源备份不能互相包含。恢复前应信任备份中的本机插件及 SQL；MySQL 插件 DDL 失败无法整体回滚，需保留失败目标并换新空数据库重试。插件自行写入的外部文件需另外备份。

## 后台定时与恢复入口

后台“存储与备份”按所选时区的每日固定时刻执行。时间采用 24 小时制，时区使用 IANA 名称，例如 `Asia/Shanghai` 或 `UTC`。默认表单为北京时间每日 03:00，保存并启用后才生效。调度器每分钟检查一次，可能比设定时刻晚一分钟启动。

每个本地日期最多自动尝试一次。手动备份不改变自动备份日期。服务在当日设定时间之后启动，会补做当天一次，不补跑过去日期；其他存储任务占用时，释放后再尝试。自动任务失败或中断后可手动重试，下一天继续定时执行。夏令时跳过设定时刻时，在跳时后补做；重复时刻仍只执行一次。

旧版“间隔小时”配置不会被猜测成某个固定时间。升级后需重新选择时间、时区并启用。原备份目录仍保留，手动备份可用。保留份数默认 0，即全部保留。设为正数后，每次后台备份成功会保留最新指定份数的完整程序备份。只有名称符合 `wishingskin-backup-时间-编号` 且通过完整校验的目录会参与清理。损坏、不完整、非程序命名和手动 CLI 备份保留。文件系统权限仍由维护者管理；异地副本需另外安排。

后台“备份列表”显示程序创建的备份，支持完整性校验和所选备份的恢复步骤。实际恢复使用停站 CLI，恢复到新的空数据库和新材质目录；后台不覆盖正在运行的站点。以下命令同时适用于后台生成的完整备份与 CLI 备份。

## 操作顺序

先停止本站所有服务实例、迁移器及其他业务写入；`--offline` 是操作人员的停写确认，程序不会远程协调停机。数据库使用只读、可重复读事务导出，文件复制期间仍须保持停写和目录不变。目标父目录必须存在，备份目录必须是全新路径，且与源材质目录互不包含。

```powershell
# 已配置当前版本的 WS_DATABASE_DRIVER / WS_DATABASE_DSN / WS_TEXTURE_DIR，
# 并停止所有应用实例、定时写入及迁移器。目标父目录必须已经存在。
New-Item -ItemType Directory -Force backups | Out-Null
./bin/wishingskin.exe backup --offline --directory backups/site-20261029

# 配置另一套空数据库；数据库先创建，材质目录选择尚不存在、独立的新路径。
$env:WS_DATABASE_DSN='connection-to-isolated-empty-target'
$env:WS_TEXTURE_DIR='data/restored-textures'
New-Item -ItemType Directory -Force data | Out-Null
./bin/wishingskin.exe migrate
./bin/wishingskin.exe restore --offline --directory backups/site-20261029
```

`backup` / `restore` 不自动升级数据库；先用对应版本的 `migrate` 初始化空目标。已有账号、会话、邀请码、业务记录或非默认设置均阻止恢复；仅允许初始化自带的角色上限 1、邮箱验证注册（或旧版默认关闭注册）、关闭全零积分规则和默认首页区块。恢复不覆盖任何已有材质目录，即使该目录为空。源备份、目标数据库和目标材质目录必须独立。当前备份恢复严格要求 schema 21 与当前程序一致。

恢复先检查清单版本、允许的表清单、行结构、行数、摘要及材质库存，再复制文件，并执行与备份迁移记录匹配的插件 SQL。核心业务行与插件数据在同一个事务中恢复；插件 DDL 在此事务之前执行，MySQL 的 DDL 不可回滚。发生 DDL 错误时，重试应使用新的空目标。材质文件名只接受受限 hash，核心表与列由程序固定。动态插件表的列、数据和包摘要单独校验。复制及入库时再次校验摘要，发生变更或数据写入错误会回滚业务事务。

## Compose 停写备份

在部署目录执行。先停止应用，再通过一次性容器运行同一版本的 CLI；数据库容器保持运行。目标父目录 `/data/backups` 已由 Compose 持久化。

```powershell
docker compose --env-file .env -f deploy/compose.postgres.yaml stop app
docker compose --env-file .env -f deploy/compose.postgres.yaml run --rm --no-deps app backup --offline --directory /data/backups/site-20261029
```

MySQL 部署将 Compose 文件名改为 `deploy/compose.mysql.yaml`。操作结束后才启动应用。`backup` 命令会拒绝覆盖已存在的目标目录；每次使用新目录名。此处的命名卷不是异地备份，需另外复制至独立故障域。

## 中断与切换

完成清单最后写入，缺少清单或清单损坏的目录不能恢复。失败导出会保留已经创建的目录，排查后选择新路径重新导出。恢复目录先写 `.restore-incomplete.json`；确认数据库提交后改名为 `.restore-complete.json`。SQL 失败时文件保留供排查，不自动删除或复用目录。重试使用新的空目录，数据库也应确认仍为空；若提交结果不确定或完成标记失败，先核对持久数据库状态，不要直接重试或清除标记。

单个 JSONL 行上限 64 MiB（含编码开销，达到该值即拒绝），清单上限 32 MiB；超过限制会停止，不截断历史。BS 快照整体仍限 64 MiB。工具逐行处理业务数据、逐个复制文件，但清单及材质索引随文件数增长。恢复期间应保留原备份，确保目标有足够空间，并避免其他进程修改文件。

核对恢复结果后再切换服务。切换后的新数据不在旧备份中；回退时需安排停写和新增数据处理。
